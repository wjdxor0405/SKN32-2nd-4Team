# 상품화를 위한 보강 제안

이탈율 예측을 실제 상품(서비스)으로 판매한다고 가정했을 때, 현재 코드베이스
(segment_discovery / churn_prediction / webapp) 기준으로 보강·개선이 필요한
부분을 정리한 문서.

> 이 문서는 README.md와 별개로 관리한다. README.md는 "이 시스템이 어떻게
> 동작하는가"를 다루는 기술 문서이고, 이 문서는 "이 시스템을 어떻게 더
> 발전시킬 것인가"를 다루는 제품/비즈니스 문서라 성격이 다르다.
>
> 세부 적용 방법이 아직 코드에 반영되지 않은 항목은 이 문서 대신
> [`webapp/PENDING_DECISIONS.md`](../webapp/PENDING_DECISIONS.md)에서
> 추적한다 — 거기서는 배경/결정/적용 대상 파일까지 구체적으로 기록하고,
> 여기서는 제품 관점의 보강 영역과 우선순위만 다룬다.

## 이미 풀고 있는 3가지 현업 갈증

상품화 논의에 앞서, 현재 구조가 이미 갖춘 강점을 먼저 짚는다.

**1. 실행 가능성(Actionability)** — 확률값만 던지지 않고, 세그먼트 +
risk_count + SHAP 핵심원인 + 프로모션 카드까지 한 화면(개인 예측 페이지)에서
묶어 보여준다. 마케터가 "그래서 뭘 보내야 하지?"를 대시보드 안에서 바로
답할 수 있다. (단, 프로모션 카드의 구체적 내용 검증은
`PENDING_DECISIONS.md`의 확정 항목 참고)

**2. 비용 효율성** — 일괄 예측 페이지에서 예상손실액(이탈확률 ×
MonthlyCharges) 기준 정렬을 제공한다. 확률은 낮아도 월요금이 높은 고객을
우선순위 상단으로 끌어올려, 한정된 예산을 가장 큰 매출 방어 효과가 있는
곳에 쓰도록 돕는다. (1개월 근사치라는 한계는 `PENDING_DECISIONS.md`의
Expected Loss 확정 항목 참고)

**3. MLOps 비용/리스크 최소화** — 통계 검증이 무거운 세그먼트/위험속성
레이어(`segment_discovery`)는 json으로 고정하고, 가벼운 XGBoost
(`churn_prediction`)만 주기적으로 재학습하는 이원화 구조다. 재학습 비용과
시스템 변동성을 줄이면서도 최신 트렌드는 놓치지 않는다.

| 레이어 | 연산 비용 | 갱신 주기 | 근거 |
|---|---|---|---|
| 세그먼트/위험속성 (`segment_discovery`) | 무거움 (순열검정 200회 + 부트스트랩 300회 × 분석A/B/Q) | 가끔 (표본이 충분히 쌓였을 때) | 통계적으로 검증된 경계는 단기간에 잘 바뀌지 않음 |
| 예측모델 (`churn_prediction/train.py`) | 가벼움 (XGBoost 1회 학습) | 정기적 (예: 매월) | 최신 고객 트렌드를 반영해야 함 |

두 레이어를 분리하지 않고 매번 통계검증까지 재실행했다면, 재학습 1회당
순열검정·부트스트랩만으로 수 분~수십 분이 소요된다. 이를 월 단위로 돌리면
클라우드 연산 비용이 누적되고, 매번 세그먼트 경계가 미세하게 흔들려 운영
일관성도 깨진다. 결과 파일(json)을 인터페이스로 고정한 덕분에, 무거운
레이어는 안정적으로 유지하면서 가벼운 레이어만 자주 돌리는 절충이
가능해진다.

## 현재 모델 성능 (참고)

`churn_prediction/outputs/latest/metadata.json` 기준 — 재학습 시 값이 바뀐다.

- AUC: 약 0.84
- 권장 분류 임계값: PR곡선 기반 자동 산출 (`find_recall_drop_threshold`)
- Precision 약 0.55, Recall 약 0.73 (test set)

3단계(세그먼트 포함) 모델이 메인이지만, 2단계(세그먼트 미포함) 대비 증분
기여(F1)는 작다. 세그먼트의 가치는 예측 성능이 아니라 해석/세그먼트 전략
수립에 있다는 점을 판매 시 명확히 포지셔닝해야 한다.

## 보강이 필요한 영역

### 데이터/모델

- **데이터 최신성 — 가장 근본적인 제약**: 현재 데이터는 절대 시점(가입일/
  이탈일) 없는 스냅샷이다. "이번 달 위험 고객"처럼 실시간성을 요구하는
  고객사에는 한계가 명확하다. 판매하려면 최소한 월 단위 스냅샷이 누적되는
  구조(매월 신규 데이터 적재 → 주기적 재학습)가 선행되어야 한다. (이 제약을
  현재 프로토타입에서 어떻게 다룰지는 `PENDING_DECISIONS.md`의 tenure 차트
  확정 항목 참고)
- **모델 성능**: Precision이 Recall 대비 낮은 편이라, 리텐션 비용을 잘못된
  대상에 쓸 위험이 있다. FN 비용은 추정했지만(`estimate_fn_cost`), FP 비용은
  추정 불가 상태다. 분류 임계값 커스터마이징 필요성은
  `PENDING_DECISIONS.md`의 위험등급 임계값 항목에서 다룬다.
- **설명 가능성**: SHAP + 프로모션 카드로 1차 액션 레이어는 갖췄지만, 이
  매핑은 사람이 정한 휴리스틱이라 실제 효과는 검증되지 않았다. 어떤
  프로모션이 실제 리텐션 성공률을 높이는지는 A/B 테스트로 별도 검증해야
  한다. 또한 5개 위험속성에 해당하지 않는데도 고위험으로 예측된 고객(예:
  tenure 자체가 핵심 원인)에는 추천할 카드가 없다.

### 시스템/운영

- **재학습 자동화**: 현재 `train.py`/`segment_discovery/app.py`는 수동
  실행이다. 운영 상품이라면 정기 재학습 스케줄러와 실패 시 알림이
  필요하다. `outputs/run_history.csv`로 이력은 남지만, 성능이 이전 버전보다
  떨어졌을 때 자동 롤백하는 안전장치는 없다.
- **API화**: 현재는 CSV 업로드 기반이다. 실제 SaaS형 상품이라면 REST API로
  고객사의 CRM/마케팅 자동화 도구와 연동할 수 있어야 한다. 대용량 배치
  처리(수만~수십만 행)에 대한 성능 테스트가 아직 없다 — SHAP 계산은 행
  수가 늘어나면 느려질 수 있다 (현재 webapp의 임시 제한 방식은
  `PENDING_DECISIONS.md`의 SHAP 계산 범위 항목 참고).
- **멀티테넌시**: 지금은 단일 데이터셋(Telco) 전용이다. 여러 고객사를
  동시에 서비스하려면 고객사별로 격리된 모델/세그먼트 규칙 저장소가
  필요하다 — 현재 구조는 `outputs/latest/` 하나뿐이라 고객사가 둘 이상이면
  덮어써진다.

### 신뢰·컴플라이언스

- **개인정보 처리**: `customerID`, 통신/결제 정보 등은 민감할 수 있는
  데이터다. 암호화 저장, 접근 권한 관리, 데이터 보존/삭제 정책이 현재
  코드에는 전혀 없다. CSV 업로드 방식은 보안을 우려하는 엔터프라이즈
  고객에게는 유출 경로로 보일 수 있어, SOC2 같은 인증 없이는 판매가
  어려울 수 있다.
- **모델 공정성(Fairness)**: `gender`, `SeniorCitizen` 같은 인구통계
  변수가 예측에 직접 사용된다. 업종/지역에 따라 차별적 영향(disparate
  impact) 검증이 법적으로 요구될 수 있는데, 현재는 검증 로직이 없다.
- **모델 카드 / 감사 추적**: "이 모델이 왜 이 고객을 고위험으로
  분류했는가"에 대한 감사 가능한 기록(모델 버전, 입력 스냅샷, SHAP 값
  저장)이 필요하다. 현재는 예측 결과만 CSV로 받을 수 있고, 재현 가능한
  이력 추적은 `predictions.csv`(버전 폴더)에 국한된다.

### 비즈니스 가치 증명

- **ROI 지표 — 1개월 단위는 갖췄지만 LTV 단위는 부족**: 예상손실액 합계와
  "상위 N명 방어 가능 손실액"을 보여주지만, 1개월치 근사다. LTV 단위 ROI로
  확장하는 문제는 `PENDING_DECISIONS.md`의 Expected Loss 확정 항목(향후
  과제 — 생존분석 기반 분석C 신설)에서 다룬다.
- **A/B 테스트 추적**: 모델 기반 리텐션 액션 vs 미적용 그룹의 실제 이탈율
  차이를 추적할 방법이 없다 — 판매 후 "효과가 있었다"를 증명하는 핵심
  자료인데 아직 없다.
- **벤치마크 부재**: 동종 업계 평균 이탈율과 비교하는 기능이 없어, 현재
  수치(이탈율 약 26.5%)가 좋은지 나쁜지 고객사가 판단하기 어렵다.
- **액션 우선순위화 — 단순 정렬은 갖췄지만 예산 제약 최적화는 아님**:
  예상손실액 기준 정렬과 "상위 N명" 슬라이더를 제공하지만, 실제 캠페인
  예산(1인당 비용 $X)이 주어졌을 때 순이익을 최대화하는 조합 최적화(배낭
  문제류)는 아니다. 예산 제약이 빡빡한 고객사라면 이 차이가 실제 ROI에
  영향을 줄 수 있다.

## 우선순위 제안 (상품화 로드맵 관점)

| 우선순위 | 항목 | 상태 | 이유 |
|---|---|---|---|
| 1 | 프로모션 카드 효과 A/B 테스트 | 미착수 | 휴리스틱 매핑이 실제 리텐션에 효과 있는지 검증 필요 |
| 2 | FP/FN 비용 반영 임계값 커스터마이징 | 보류 — 타 작업자와 논의 예정 (`PENDING_DECISIONS.md` 추적 중) | 리텐션 비용 낭비를 막아야 ROI를 증명 가능 |
| 3 | LTV 단위 ROI (생존분석 기반) | 1개월 단위만 구현 (`PENDING_DECISIONS.md` 향후 과제로 분리) | 영업·구매결정 단계 설득력 강화 |
| 4 | 정기 재학습 자동화 + 성능 모니터링 | 미착수 | 데이터 드리프트 대응 없이는 신뢰 유지 불가 |
| 5 | API화 + 멀티테넌시 | 미착수 | 여러 고객사 대상 SaaS 형태로 확장하려면 필수 |
| 6 | 개인정보/공정성 컴플라이언스 | 미착수 | 엔터프라이즈 판매 시 계약 단계에서 요구됨 |

1~3순위는 "이 모델이 실제로 돈을 절약해준다"를 증명하는 데 직결되어 구매
결정 단계에서 가장 먼저 요구될 항목이고, 4~6순위는 판매 이후 확장·신뢰
단계에서 필요해지는 항목이다.

고객사 요구사항에 따라 우선순위는 달라질 수 있다.
