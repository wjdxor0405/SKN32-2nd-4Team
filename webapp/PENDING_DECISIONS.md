## [확정] tenure 차트는 해석 A(횡단면)로 유지, 라벨링만 보강

**배경**: 데이터에 가입일/이탈일 같은 절대 시점이 없는 스냅샷이라 "코호트가
시간이 지나며 어떻게 줄어드는가"를 보여주는 진짜 시계열(해석 B, 가입월 합성)은
만들 수 없다. tenure를 거꾸로 환산해 가짜 가입월을 합성하는 것도 검토했으나,
이미 이탈해서 데이터셋에 없는 고객은 애초에 셀 수 없어 코호트 막대 하나하나가
근거가 약한 추정치가 된다는 점을 시각 비교(두 차트 목업)로 확인하고 기각.

**결정**: 현재 01번 페이지의 tenure-이탈율 차트(횡단면 집계, 이미 구현됨)를
그대로 유지하되, 이게 "코호트 추이"가 아니라 "현재 시점 스냅샷의 단면"이라는
점을 명시적으로 라벨링한다.

**적용 대상**: `webapp/pages/01_세그먼트_분석.py`

**적용 방법**:
1. 차트 캡션을 다음으로 교체(또는 보강):
   "현재 보유 고객 기준 가입 경과월별 이탈율 (특정 시점 스냅샷, 코호트 추이 아님)"
2. 페이지 하단에 로드맵 문구 추가:
   "가입일·이탈일이 누적되면 실제 코호트 추이 분석(예: 2025년 1월 가입자가
   N개월 후 몇 % 남았는가)으로 확장 가능합니다."

**상태**: ✅ 반영 완료 (01번 페이지 캡션·로드맵 안내 추가).

## [확정] 프로모션 매핑 — 행동 카테고리는 구체적으로, 숫자는 placeholder임을 명시

**배경**: `PROMOTION_PLAYBOOK`의 "2개월 할인", "월 2,000원 할인", "1개월 무료
체험권" 같은 숫자는 Claude가 그럴듯해 보이려고 임의로 채운 값이지, 원가 구조나
고객사 마진율 등 어떤 근거도 없다. 분석A/B/서브트랙Q처럼 통계 검증을 거친
다른 수치들과 달리, 이 숫자는 코드 안에 들어간 "가짜로 그럴듯한 값"이라
같은 신뢰도로 보이면 위험하다는 점을 지적받고 확인.

완전 추상화("할인 제공" 정도로만 표현)도 검토했으나, 그러면 "마케터가 무엇을
해야 하는가"에 답하는 힘이 약해져 이 기능을 만든 원래 목적(실행 가능성)과
충돌한다는 문제가 있어 기각.

**결정**: 절충안 채택.
- 행동 카테고리(자동이체 전환 유도, 체험권 제공, 캐시백 등 액션의 종류)는
  구체적으로 유지한다.
- 할인폭·금액 등 구체적 숫자는 placeholder임을 화면에 명시한다.

**적용 대상**: `webapp/utils.py`의 `PROMOTION_PLAYBOOK` 딕셔너리,
`webapp/pages/02_개인_예측.py`의 프로모션 카드 렌더링부

**적용 방법** (두 가지 중 택1, 종합 적용 시 결정):
1. 카드 문구의 숫자 자리를 비워서 표시: "자동이체 전환 시 월 [할인액] 할인 쿠폰"
2. 숫자는 유지하되, 카드 옆에 작은 라벨 추가: "예시 값 — 실제 운영 시 마진
   구조에 맞게 조정 필요"

**상태**: ✅ 반영 완료 (적용 방법 1 채택 — 숫자 자리를 `[ ]` placeholder로 표시).

## [확정] Expected Loss — 1개월 단위 유지, "LTV 반영 시 더 커질 수 있음" 명시

**배경**: "이탈확률 × MonthlyCharges"를 1개월치 손실로 근사하는 현재 방식을
LTV(잔여 생애주기 반영) 버전으로 확장할지 검토. 잔여 개월수 추정 후보를
데이터로 직접 확인:
- Contract 기반 "남은 약정 기간": One year/Two year는 계산 가능하나,
  Month-to-month(전체의 약 55%, 가장 위험한 그룹)는 약정 개념 자체가 없어
  추정 불가 — 가장 필요한 곳에서 작동하지 않음.
- Contract별 평균 tenure를 "기대 생애주기"로 사용: `evaluate.py`의
  `estimate_fn_cost()`(전체 모델 단위 FN비용 추정)와 개념이 겹쳐 같은 화면에
  서로 다른 두 숫자가 떠 있으면 혼란 위험. 게다가 단순 평균은 이미 이탈한
  고객은 짧게, 안 한 고객은 길게 잡히는 편향이 있어 본래는 생존분석
  (Kaplan-Meier 등)이 필요한 문제 — `requirements.txt`에 `lifelines>=0.27`이
  명시되어 있으나 실제 코드 어디에도 import되지 않음(설계 단계에서 검토 후
  보류된 흔적으로 추정).

대충 평균을 곱해 LTV를 내면, 프로모션 매핑 건(위 항목)에서 지적했던 "가짜로
그럴듯한 숫자" 문제가 그대로 재발한다는 점이 가장 큰 기각 사유.

**결정**:
- Expected Loss는 1개월 단위(`이탈확률 × MonthlyCharges`)를 그대로 유지한다.
- 화면에 "이건 1개월 근사치이며, 잔여 생애주기(LTV)를 반영하면 실제 손실액은
  더 클 수 있다"는 점을 명시한다.
- 정확한 LTV 계산(생존분석 기반)은 지금 범위에 넣지 않고 향후 과제로 분리한다.

**적용 대상**: `webapp/utils.py`의 `add_expected_loss()` 주변 주석(이미 일부
명시되어 있음, 문구 보강 필요), `webapp/pages/02_개인_예측.py`와
`webapp/pages/03_일괄_예측.py`의 예상손실액 표시부에 캡션 추가

**적용 방법**:
- 예상손실액 메트릭 옆에 caption으로 "1개월 근사치 · 약정 잔여기간(LTV) 반영 시
  더 클 수 있음" 같은 문구 추가

**향후 과제 (지금 범위 밖, 별도 트랙으로 분리)**:
- `segment_discovery`에 분석C 격으로 "잔여 생애주기 추정" 레이어를 신설하고,
  Kaplan-Meier 생존분석으로 Contract×세그먼트별 잔여 개월 기대값을 통계적으로
  추정. 기존 분석A/B처럼 순열검정·부트스트랩 검증을 거쳐 `segment_rules.json`에
  결과를 추가하는 방식이 이 프로젝트의 기존 설계 원칙과 일관됨.
- 이 작업이 완료되기 전까지는 LTV 단위 Expected Loss를 대시보드에 넣지 않는다.

**상태**: ✅ 반영 완료 (02·03번 페이지에 LTV 안내 캡션 추가). 향후 과제
(생존분석 기반 LTV 계산)는 미착수 상태로 유지.

## [확정] SHAP 계산 범위 — 상위 N명 제한 제거, 전체 기본 계산 + 대용량 안전장치만 유지

**배경**: "전체 고객에 SHAP을 계산하면 느려질 수 있다"는 가정만으로 상위
5~50명(슬라이더 기본 10명)으로 임의 제한해 구현했었다. 실측 없이 내린
보수적 판단이었다는 지적을 받고 직접 측정:

| 입력 행 수 | SHAP 계산 소요시간 | 비고 |
|---|---|---|
| 1건 | 0.93초 | TreeExplainer 최초 초기화 비용 포함(세션당 1회, 캐싱됨) |
| 10건 | 0.03초 | |
| 100건 | 0.06초 | |
| 1,000건 | 0.29초 | |
| 7,043건 (원본 데이터 전체) | 1.85초 | |
| 35,215건 (5배 시뮬레이션) | 9.38초 | |

초기화 이후로는 건당 약 0.27ms로 거의 선형 증가. 일반 추론
(`predict_churn`)보다 약 39배 느리지만, 절대 시간으로는 원본 데이터 전체
(7,043건)도 약 1.85초로 Streamlit 스피너 한 번 도는 수준이면 충분히 감당
가능. 당초 제한했던 5~50명 구간은 실측 결과 7천 건 전체와 사용자 체감상
차이가 없는 수준이라, 제한 자체가 불필요한 UI 복잡도였음을 확인.

**결정**:
- 상위 N명 제한 슬라이더와 "핵심 원인 계산하기" 버튼(클릭 유도)을 제거한다.
- 일괄 예측 결과에 SHAP 핵심원인 컬럼을 업로드된 고객 전체에 대해 기본으로
  항상 포함한다.
- 다만 매우 큰 업로드(예: 5만 건 이상, 선형 추세로 약 13초 이상 소요 예상)에
  대비해 안전장치를 남긴다 — 임계 행 수 이상이면 SHAP 계산을 자동 스킵하고
  "데이터가 너무 커 핵심원인 계산을 생략했습니다" 같은 안내 문구를 표시.

**적용 대상**: `webapp/pages/03_일괄_예측.py` — `explain_n` 슬라이더와
"핵심 원인 계산하기" 버튼 제거, 결과 테이블에 핵심원인 컬럼 기본 추가,
행 수 임계치 체크 로직 추가

**적용 방법**:
1. 예측 직후 `explain_prediction_per_row(df_raw, top_n=1)`를 전체 행에 대해
   바로 호출 (현재처럼 상위 N명만 잘라서 호출하지 않음)
2. 행 수가 임계치(예: 50,000건)를 넘으면 SHAP 호출을 건너뛰고 안내 메시지만
   표시 — 정확한 임계값은 종합 적용 시 다시 한번 가볍게 재측정해 확정

**상태**: ✅ 반영 완료. 임계값 50,000건으로 적용(`SHAP_ROW_LIMIT`), 추가
재측정 없이 그대로 채택. 상위 N명 슬라이더·버튼 제거하고 결과 테이블에
핵심원인 컬럼 기본 포함 확인.

## [확정] TotalCharges 자동계산 — 로직 유지, 신규 고객 추정 오차 안내 보강

**배경**: 개인 예측 폼의 `tenure × MonthlyCharges` 자동계산이 가입 초기
프로모션 할인 등으로 실제 누적액과 다를 수 있다는 우려가 있어, 원본 데이터로
직접 오차를 측정:

| tenure 구간 | 단순곱셈 근사 대비 평균 절대오차율 |
|---|---|
| 0~6개월 | 4.4% |
| 6~12개월 | 5.3% |
| 12~24개월 | 3.8% |
| 24~48개월 | 2.7% |
| 48~72개월 | 1.8% |

tenure가 짧을수록(특히 02번 페이지가 주로 다루는 신규 가입 후보 시나리오와
겹치는 구간) 오차율이 커지고, 최악의 경우 -45%~+36%까지 벌어짐(전체 평균은
0%에 가깝지만 분포 폭이 넓음). 다만 이 오차가 실제 예측 결과에 미치는 영향을
SHAP으로 직접 흔들어 확인한 결과, 가장 극단적인 -45% 오차를 줘도 이탈확률이
0.663→0.677로 1.4%p 변화하는 수준 — TotalCharges는 모델 입력 중 영향력이
작은 변수라 예측 자체를 왜곡할 위험은 낮음.

**결정**:
- 자동계산 로직(`tenure × MonthlyCharges`)은 유지한다 — 모델 예측에 미치는
  실질 영향이 작다는 게 실측으로 확인됨, 완전 제거는 사용자 번거로움 대비
  실익이 작음.
- 다만 "이 값은 추정치이며 신규 고객일수록 오차가 클 수 있다"는 점을
  입력 필드 캡션에서 더 명확히 안내한다.
- 사용자가 정확한 값을 알 경우 직접 덮어쓸 수 있는 현재 구조(number_input)는
  그대로 유지.

**적용 대상**: `webapp/pages/02_개인_예측.py`의 `total_charges` 입력 필드

**적용 방법**: 입력 필드 라벨/캡션을 다음으로 보강:
"누적 청구액 ($, 비워두면 tenure×월요금으로 추정 — 신규 고객일수록 실제값과
차이가 클 수 있음)"

**상태**: ✅ 반영 완료 (02번 페이지 `total_charges` 필드 라벨 갱신).

## [확정] 운영 제안 줄글 답변 → `docs/improvement_proposal.md`로 분리, 보관 완료

**배경**: `04_운영_제안.py` 페이지를 삭제하고 줄글 답변으로 대체했으나, 그
내용을 어디에도 파일로 남기지 않은 상태였다. README.md에 추가하는 안도
검토했으나, README.md는 현재 다른 작업자가 작업 중인 파일이라 건드릴 수
없고, 조만간 그 작업자와 별도로 논의해 바뀔 예정이라는 점이 확인됨.

**결정**: README.md는 건드리지 않는다. 운영 제안 내용은 `docs/` 폴더에
별도 문서로 분리한다 — README(기술 문서: 어떻게 동작하는가)와
improvement_proposal(제품 문서: 어떻게 발전시킬 것인가)의 성격이 달라
분리하는 게 이 프로젝트의 기존 관심사 분리 원칙과도 일관된다.

겹치는 내용 병합 처리:
- 운영 제안의 "FP/FN 비용 반영 임계값" 항목 → 아래 "위험등급 임계값(risk_tier)"
  항목에 병합
- 프로모션 카드 휴리스틱, Expected Loss 1개월 단위 한계 → 이미 위에서 확정된
  항목을 중복 서술하지 않고 improvement_proposal.md에서 링크로만 참조

**적용 대상**: `docs/improvement_proposal.md` (신규 생성, 완료)

**적용 방법**: 완료. 강점 3가지(실행가능성/비용효율성/MLOps), 모델 성능

## [확정] 위험등급 임계값(risk_tier) — 숫자는 유지, 조정 가능 여부는 추후 타 작업자와 논의

**배경**: `utils.py`의 `risk_tier()`에서 고위험 ≥0.6, 중위험 ≥0.32 기준이
근거 없이 정해진 게 아닌지 확인 필요성이 제기됨. 실제 예측 결과로 분리력을
검증:

| 등급 | 구간 | 인원 (비율) | 실제 이탈율 |
|---|---|---|---|
| 저위험 | [0, 0.32) | 4,520명 (64.2%) | 9.5% |
| 중위험 | [0.32, 0.6) | 1,549명 (22.0%) | 45.1% |
| 고위험 | [0.6, 1.0] | 974명 (13.8%) | 76.0% |

세 구간의 실제 이탈율이 명확히 분리되어, 0.32(모델의
`recommended_threshold`에서 가져온 값)와 0.6 모두 결과적으로 잘 작동하는
경계임을 확인. 다만 저위험군이 전체의 64.2%로 너무 넓어, "한정된 예산으로
상위 몇 %만 본다"는 운영 맥락에서는 고정 구간이 비즈니스 상황(고객사 예산
규모 등)에 안 맞을 수 있다는 문제는 별개로 남음.

이와 별개로, 운영 제안에서 짚었던 "FP/FN 비용을 반영해 모델 분류
임계값(`recommended_threshold`) 자체를 재계산하는 기능"은 webapp이 아니라
`churn_prediction/evaluate.py`(모델 평가 레이어) 변경이 필요해 범위가
다르다는 점도 확인됨.

**결정**:
- risk_tier의 두 기준값(0.32, 0.6)은 숫자 그대로 유지한다 — 실측으로 분리력이
  확인됨.
- "하드코딩 대신 대시보드에서 사용자가 직접 조정 가능하게 만들지"는 지금
  결정하지 않는다 — webapp 단독으로 정할 사안이 아니라 다른 작업자(README를
  포함한 프로젝트 전반을 다루는 쪽)와 함께 논의가 필요하다고 판단해 보류.
- 모델 분류 임계값(`recommended_threshold`) 재계산 기능은 webapp 범위 밖의
  별도 과제로 분리한다 — `churn_prediction/evaluate.py` 변경이 필요하므로
  이 결정 추적 문서(webapp 범위)와는 별도 트랙에서 다룰 것.

**적용 대상**: 없음 (현재 숫자 유지, 코드 변경 불필요)

**보류 사유 / 논의 필요 대상**: risk_tier를 사용자 조정 가능하게 만들지는
README.md 작업 중인 다른 작업자와 함께 논의 예정. 이 논의가 결론 나기 전까지
risk_tier는 현재 하드코딩 상태(0.32/0.6)를 그대로 유지한다.

**상태**: 보류 확정 — "지금은 결정하지 않는다"는 결정. 추후 타 작업자와의
논의 결과가 나오면 이 항목을 갱신한다.

## [확정] "프로토타입 vs 실제 상품" 원칙의 적용 범위 — 타 작업자와 논의할 사항으로 분리

**배경**: tenure 차트 건에서 "지금은 고객사에게 보여줄 프로토타입이니, 데이터
제약(절대 시점 없음)을 받아들이고 그 안에서 풀자"는 원칙이 합의됐다. 이 원칙을
다른 페이지·다른 트레이드오프에도 일반적으로 적용할지가 미결로 남아있었음.

원래 있던 두 가지 결정 필요 사항 중 첫 번째("SHAP 비용 문제, 프로토타입이니
제한할지 vs 비동기 고려할지")는 이미 위 "SHAP 계산 범위" 확정 항목에서
실측으로 해소됨 — 가정이 아니라 데이터로 확인한 결과 제한 자체가 불필요했음.

남은 두 번째 사항("앞으로 비슷한 트레이드오프가 나올 때 쓸 일반 원칙")은
webapp 코드 하나의 문제가 아니라 프로젝트 전체에 적용될 작업 방식에 대한
합의라, webapp 범위에서 혼자 결정하지 않기로 함. 위 "위험등급 임계값"
항목과 같은 성격(webapp 단독으로 정할 사안 아님)이라 함께 논의하는 게
자연스럽다고 판단.

**결정**: 일반 원칙 정립은 지금 확정하지 않고, 다른 팀원과 논의할 사항으로
넘긴다.

**논의 시작점 (참고용 의견, 결정 아님)**: 데이터·기술적 제약(예: 절대 시점
없음)은 프로토타입 단계에서 받아들이되 사용자에게 숨기지 않고 명시한다.
반면 "느릴 것이다", "비쌀 것이다" 같은 비용·성능에 대한 가정은 프로토타입
이라는 이유로 미리 제한해버리지 않고, 가능하면 먼저 실측한 뒤 제한 여부를
결정한다 — 전자는 지금 검증할 방법이 없는 사실의 한계이고, 후자는 검증
가능한데 안 해본 추측이기 때문(SHAP 계산 범위 건이 실제 사례).

**적용 대상**: 없음 (webapp 범위 밖, 프로젝트 전체 작업 방식)

**보류 사유 / 논의 필요 대상**: 위 "위험등급 임계값" 항목과 함께, README.md
작업 중인 다른 작업자와 논의 예정.

**상태**: 보류 확정 — "지금은 결정하지 않는다"는 결정. 추후 타 작업자와의
논의 결과가 나오면 이 항목을 갱신한다.

## [수정] 03번 페이지 — 업로드 행 5건 미만일 때 슬라이더 크래시

**증상**: `streamlit.errors.StreamlitAPIException: Slider 'min_value' must be
less than the 'max_value'.` — 샘플 CSV(1행)를 그대로 업로드하면 발생.

**원인**: `budget_n` 슬라이더가 `min_value=5`로 고정인데
`max_value=min(200, len(result))`라서, 업로드 행이 5건 미만이면
`min_value(5) > max_value(행수)`가 되어 Streamlit이 예외를 던짐.

**수정**: 결과 행이 5건 미만이면 슬라이더를 표시하지 않고
`budget_n = len(result)`(전체)로 대체. 5건 이상일 때만 기존 슬라이더 사용.
n=1,2,4,5,6,20,200,300 전 구간 시뮬레이션으로 안전성 확인.

**적용 대상**: `webapp/pages/03_일괄_예측.py` (완료)
